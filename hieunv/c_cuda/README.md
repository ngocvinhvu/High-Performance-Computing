# Library-free version: sequential C (CPU) and hand-written CUDA (GPU)

The course rules do not allow ready-made parallel libraries. The PyTorch code in `../code` measures MKL/oneDNN on the
CPU and cuBLAS/cuDNN on the GPU. It stays as a reference. This folder re-implements the same experiments by hand:

| File | Content |
|---|---|
| `common.h` | Shared plain C: layer constants, clocks, random data, statistics, CSV/JSON output, command line, float64 reference kernels for the checks, Caffe `im2col` |
| `bench_seq.c` | Sequential C, 1 thread: no BLAS, no OpenMP, no library beyond libc/libm |
| `bench_cuda.cu` | CUDA, all kernels hand-written. It links only the CUDA runtime: no cuBLAS, cuDNN, Thrust or CUB |
| `Makefile` | `make seq`, `make cuda ARCH=sm_75`, `make check` |

The experiment plan and the predictions written before any run are in [`../PLAN_C_CUDA.md`](../PLAN_C_CUDA.md).

## Implementations

| Experiment (CSV) | CPU, `bench_seq` | GPU, `bench_cuda` |
|---|---|---|
| `conv` (paper Fig 1–2), batch 1–256 | **`caffe`**: per image, `im2col` then the blocked GEMM + bias. `direct`: the convolution loops | **`caffe`**: per image, one `im2col` kernel plus one GEMM kernel (2 launches). `batched`: 2 launches for the whole batch. `direct`: one thread per output, weights in constant memory |
| `fc` matvec (Fig 3–4), n = 256–16384 | `matvec_naive`: one accumulator. **`matvec`**: 32 independent accumulators | `matvec_naive`: one thread per row (not coalesced). **`matvec`**: one warp per row, float4, shuffle reduction |
| `fc` gemm (Fig 3 caption) | `gemm_naive` (i, j, k), `gemm_ikj` (loop interchange), **`gemm`**: packed 16-column panel of B, 4×16 tile of C in registers, k blocks of 256 | `gemm_naive` (one thread per element), `gemm_tiled` (16×16 shared-memory tiles), **`gemm`**: 48 or 64 × 64 tiles, 12 or 16 sums per thread in registers |
| `bw` | `sum`, `dot`, `copy`, `triad`, `matvec` on n² floats | Same; reductions in two passes (blocks, then one block) |
| `fcb` | (n×n)·(n×B): `mm1` = `matvec`, otherwise `gemm` | Same |
| `step` | `im2col` only, GEMM only, `caffe` | Same |

Bold marks the main series: the one compared with the paper and between the two devices. The other implementations
form the "naive → optimized" ladder of each device. The CSV columns are those of `../code/common.py`, so the same
analysis code can read both versions.

## Correctness

Each program checks every kernel against a float64 reference on the CPU before timing anything, and exits with code 1
if one check fails. The checks use odd shapes at tile edges, K larger than one block, both register-tile shapes,
batched GEMM, `im2col` compared bit for bit, the three convolutions, matvec on both the scalar and the float4 path, and
reductions with a tail. `--check-only` runs only the checks.

## Build and run

Kaggle: use `../kaggle/hpc_c_cuda_kaggle.ipynb`, generated by `../code/make_c_cuda_notebook.py`. It builds, prints `ldd`
for both programs, runs the checks, then 3 runs: GPU first with the NVML clock log, then CPU.

Linux or WSL (gcc only):

```bash
make seq
./bench_seq --check-only
./bench_seq --machine laptop --outdir ../results/laptop/seq_quick --quick
./bench_seq --machine laptop --outdir ../results/laptop/seq1_<stamp> --order-seed 1
```

Flags: `-O3 -march=native -std=c11 -ffp-contract=fast -fno-tree-loop-distribute-patterns`.
- `-ffp-contract=fast` lets gcc fuse a·b + c into FMA instructions. ISO C mode turns this off by default, and MKL and
  the CUDA kernels (`fmaf`) use FMA.
- `-fno-tree-loop-distribute-patterns` stops gcc from replacing the copy loop with `memcpy`.
- There is no `-ffast-math`, so sums are never reordered: only code that has independent sums by construction is
  vectorized.
The compiler's SIMD stays within one core: the program never creates a thread, and it records
`/proc/self/status` → `Threads` in `log_seq.txt` and `env_seq.json`.

## Measurement (same rules as the PyTorch version)

- 3 warm-up runs, then timed runs: 30 on the GPU, 10 on the CPU (Kaggle notebook). Times are the host wall clock.
- GPU: synchronize before and after each run; `issue_ms` is the time until the launches return. Data is already on
  the device, and copies are not timed. Before each implementation, the hand-written GEMM keeps the GPU busy for 5 s.
- Sizes are shuffled with `--order-seed`, the run number. `t_start` and `t_end` are Unix times, aligned with
  `gpu_clocks.csv`.
